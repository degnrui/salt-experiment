# 课堂实验设计记录系统设计

## 目标

在保留现有学生实验操作页面的基础上，增加一个可部署到服务器的课堂系统，使教师能够在自己的电脑上查看各学生小组的实验设计提交记录和全班统计结果。

## 用户角色

### 教师

- 使用教师账号登录。
- 创建课堂并生成多个小组码。
- 在课堂看板中查看各组所有提交历史、每次设计详情、判定结果和错误原因。
- 查看按任务和错误类型汇总的统计数据。

### 学生小组

- 在平板上输入教师提供的小组码进入课堂。
- 使用现有实验页面完成设计。
- 每次点击“确认设计”都向服务器提交一条记录，无论正确或错误都保留。

## 第一版范围

### 包含

- 教师登录。
- 教师创建课堂。
- 课堂生成多个小组码。
- 学生通过小组码进入对应课堂。
- 学生提交实验设计记录。
- 服务器保存完整提交历史。
- 教师查看小组提交历史和统计汇总。

### 不包含

- 学生个人账号体系。
- 班级、学期、学校多层级管理。
- WebSocket 实时推送。
- 自动生成教学评价报告。
- 导出 Excel 或 PDF。

## 系统结构

### 前端

- `学生端`
  - 复用现有实验操作页面。
  - 新增组码进入页。
  - 新增提交逻辑，将当前实验设计状态发送到后端。
- `教师端`
  - 登录页。
  - 课堂列表页。
  - 课堂详情页。
  - 小组记录详情区。
  - 统计汇总区。

### 后端

- 教师认证接口。
- 课堂与小组码管理接口。
- 学生提交接口。
- 教师查询接口。
- 统计聚合逻辑。

### 数据库

- 持久化教师、课堂、小组、提交记录。
- 第一版可使用关系型数据库，便于后续统计和筛选。

## 核心数据模型

### Teacher

- `id`
- `username`
- `password_hash`
- `created_at`

### Classroom

- `id`
- `teacher_id`
- `name`
- `created_at`

### Group

- `id`
- `classroom_id`
- `name`
- `join_code`
- `created_at`

### Submission

- `id`
- `classroom_id`
- `group_id`
- `task_type`
- `beaker_a`
- `beaker_b`
- `salt_timing`
- `stir_timing`
- `is_correct`
- `error_types`
- `submitted_at`

其中：

- `task_type` 取值为 `stir`、`temp`、`size`。
- `beaker_a`、`beaker_b` 记录水类型、水量、盐类型、盐量、是否搅拌。
- `error_types` 为错误类型数组，便于一条记录同时保留多个错误。

## 提交判定规则

每次提交都由后端根据提交内容重新判定，避免只信任前端。

### 通用规则

- A、B 两组都必须包含水和盐。
- A、B 两组水量必须相同。
- A、B 两组盐量必须相同。
- 如果两边都加盐，则加盐时机必须为同时。
- 如果两边都搅拌，则搅拌时机必须为同时。

### 探究搅拌

- A、B 的搅拌状态必须不同。
- 水类型必须相同。
- 盐类型必须相同。

### 探究温度

- A、B 的水类型必须不同。
- 盐类型必须相同。
- 搅拌状态必须相同。

### 探究颗粒

- A、B 的盐类型必须不同。
- 水类型必须相同。
- 搅拌状态必须相同。

## 错误类型

- `missing_materials`：缺少必要材料。
- `unequal_quantities`：水量或盐量不一致。
- `target_not_varied`：探究变量没有形成对比。
- `control_variables_mismatch`：无关变量没有控制一致。
- `salt_timing_mismatch`：加盐时机不一致。
- `stir_timing_mismatch`：搅拌时机不一致。

教师端同时显示机器编码和中文解释，前端默认只展示中文。

## 教师端功能设计

### 课堂概览

- 展示课堂名称、小组数量、总提交次数、正确提交次数、正确率。
- 按任务展示 `探究搅拌 / 探究温度 / 探究颗粒` 的提交次数与正确率。
- 展示错误类型统计排行。

### 小组记录

- 按小组查看所有提交历史。
- 每条记录展示：
  - 提交时间
  - 探究任务
  - A、B 两组设计
  - 正确或错误
  - 错误原因

### 刷新方式

- 第一版采用轮询刷新。
- 教师端每隔数秒自动重新拉取数据，并提供手动刷新按钮。
- 后续若课堂使用中需要更强实时性，可升级为 WebSocket。

## 学生端改造点

- 进入实验页面前输入小组码。
- 成功加入后在页面顶部显示当前小组名称。
- 当前“确认设计”按钮改为：
  1. 读取当前实验状态。
  2. 调用后端提交接口。
  3. 根据后端返回的判定结果展示成功弹窗或错误提示。
- 保留原有拖拽交互和视觉反馈。

## 接口草案

### 教师

- `POST /api/auth/login`
- `POST /api/classrooms`
- `GET /api/classrooms`
- `GET /api/classrooms/:id`
- `POST /api/classrooms/:id/groups`
- `GET /api/classrooms/:id/dashboard`
- `GET /api/classrooms/:id/submissions`

### 学生

- `POST /api/student/join`
- `POST /api/submissions`

## 统计口径

- `总提交数`：课堂下所有提交记录数量。
- `正确率`：正确提交数 / 总提交数。
- `按任务正确率`：某任务下正确提交数 / 该任务总提交数。
- `错误类型次数`：某错误类型在全部提交中出现的次数；一条记录可同时计入多个错误类型。
- `小组提交历史`：按提交时间倒序展示，不覆盖旧记录。

## 异常处理

- 小组码无效时拒绝进入并提示重新输入。
- 未登录教师访问教师端接口时返回未授权。
- 提交数据缺字段时后端返回校验错误。
- 网络失败时学生端提示提交失败，不误报成功。
- 教师端拉取失败时保留旧数据并提示刷新异常。

## 测试重点

- 三类任务的正确案例均能被判定为正确。
- 各错误类型都能被准确识别。
- 一次提交可以同时记录多个错误。
- 学生每次点击确认都会新增记录，不覆盖历史。
- 教师只能查看自己的课堂。
- 统计数字与原始提交记录一致。
